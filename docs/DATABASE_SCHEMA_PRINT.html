1. Architectural Guarantees & System Invariants

The database schema is constructed by first-principles to provide an uncompromising transactional backbone for enterprise carpooling. Every operational query, corridor match, seat allocation, and administrative action conforms to four foundation invariants:

1. Strict Multi-Tenant Boundary Isolation

Every operational table maintains an explicit, non-nullable organization_id UUID referencing organizations.id. All unique and performance indexes are compound-keyed with organization_id, ensuring absolute cross-tenant data isolation and preventing data leakage across corporate entities.

2. Clean Domain & Asset Separation

Identity (users) is decoupled from physical assets (vehicles), scheduled journeys (rides), corridor vectors (ride_routes), and booking tenders (ride_requests). Commuter pickup/drop coordinates are never stored directly on the ride; routes are never opaque strings.

3. Concurrency Safety & Seat Integrity

Seats cannot be oversold under concurrent load. Enforced via database-level check constraints (chk_available_seats_non_negative: available_seats >= 0 and available_seats <= total_seats_offered), combined with PostgreSQL row-level pessimistic locking (FOR UPDATE) in transactional workflows.

4. Geospatial Corridor Optimization

Spatial routes are structured with 4D bounding boxes (min/max latitude/longitude) and ordered waypoint nodes (route_waypoints). Search queries execute sub-millisecond bounding box containment tests before corridor polygon calculations, eliminating expensive table scans.

3. Domain Subsystems & Lifecycle Interconnections

3.1 Identity, Tenancy & Vehicle Ownership

The tenant root is organizations. Every employee record in users is bounded by its parent organization. Capabilities (can_ride, can_drive, is_org_admin) are maintained in a 1-to-1 extension table user_capabilities to keep the core identity table compact and audit-friendly. Vehicles are owned by users (vehicles.owner_id) and must be verified before drivers can schedule rides with them.

3.2 Scheduled Rides, Corridors & Bounding Box Spatial Indexing

When a driver posts a ride, three tightly coupled entities are populated:

  • rides: Tracks temporal schedules, status, and seat counters (available_seats and total_seats_offered).
  • ride_routes: Contains the departure and arrival coordinates, total route duration, distance, polyline, and geographic bounding box (min_latitude, max_latitude, min_longitude, max_longitude).
  • route_waypoints: Normalized intermediate stops along the corridor with cumulative estimated_arrival_offset_seconds.

During search, the query uses the indexed bounding box coordinates to quickly eliminate 99% of non-matching rides before executing corridor detour evaluations.

3.3 Request Negotiation, Optimistic Concurrency & Pessimistic Seat Locking

Passengers submit requests via ride_requests, referencing their chosen pickup_points and drop_points. When a driver accepts a request, concurrency control prevents race conditions:

Atomic Acceptance & Booking Workflow (PostgreSQL Transaction)

1. SELECT * FROM ride_requests WHERE id = $1 FOR UPDATE; (Row-level exclusive lock on request)

2. SELECT * FROM rides WHERE id = $2 FOR UPDATE; (Row-level exclusive lock on ride)

3. Verify available_seats >= requested_seats and driver ownership.

4. Decrement available_seats = available_seats - requested_seats on rides.

5. Transition request status to ACCEPTED.

6. Insert confirmed booking record into ride_passengers.

7. Commit transaction. If available seats violate constraints, PostgreSQL raises an invariant error and aborts.
